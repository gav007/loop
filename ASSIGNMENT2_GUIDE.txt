ASSIGNMENT 2: ULTRA-BASIC CHECKLIST FOR LOOP
============================================

This guide turns the backend part of the assignment into 20 very small tasks.
The idea is simple:

1. Do one tiny task.
2. Test that one thing.
3. Make one Git commit.
4. Move to the next task.

No code is included here. This is only a plain-English plan using the file names already in this project.

Current project files that matter most:
- templates/login_page.php
- templates/dashboard.php
- templates/register.php
- backend/db_connect.php
- backend/login_handler.php
- backend/logout.php

--------------------------------------------------
PHASE 1: GET ORGANISED BEFORE WRITING LOGIC
--------------------------------------------------

STEP 1: Confirm the login flow on paper
Goal: Be clear about the route before changing anything.
Files to check: templates/login_page.php, backend/login_handler.php, templates/dashboard.php
Hint: Write the flow in one sentence: login form -> handler -> validation -> database check -> session -> redirect.
Suggested commit: docs: map basic login flow

STEP 2: Use one database connection file only
Goal: Avoid confusion about which file connects to MySQL.
Files to check: backend/db_connect.php
Hint: Keep a single connection file. If it prints success text, remove that later because output can break redirects.
Suggested commit: chore: confirm single db connection file

STEP 3: Decide your session names before using them
Goal: Keep session data simple and consistent.
Files to plan around: login handler, login page, dashboard, logout
Hint: Pick a small set of names only, such as login flag, user id, username, error message, and old email.
Suggested commit: docs: plan session keys

STEP 4: Decide what your XSS cleanup step means
Goal: Understand what you are protecting against.
Files to plan around: backend handlers and pages that display user data
Hint: Keep it basic. Clean incoming text with trimming, and escape output with special-character conversion when showing values on the page.
Suggested commit: docs: plan input cleaning and output escaping

STEP 5: Write down the minimum login rules
Goal: Know exactly what counts as valid input.
Files to check: templates/login_page.php
Hint: Minimum rules are enough: email must not be empty, password must not be empty, email must look like a real email.
Suggested commit: docs: list minimum validation rules

--------------------------------------------------
PHASE 2: BUILD THE LOGIN VALIDATION IN TINY STEPS
--------------------------------------------------

STEP 6: Create or tidy the login handler entry point
Goal: Have one backend file that only processes the login form.
Files to change: backend/login_handler.php
Hint: This file should act as the decision-maker for login, not as a page the user reads directly.
Suggested commit: feat: prepare login handler

STEP 7: Check that the form submits the right way
Goal: Make sure the handler only accepts a real form submission.
Files to check: templates/login_page.php, backend/login_handler.php
Hint: The form should submit to the login handler, and the handler should only process a proper POST request.
Suggested commit: feat: guard login handler by request type

STEP 8: Read the submitted email and password
Goal: Capture the form values once and keep the flow simple.
Files to change: backend/login_handler.php
Hint: Read the two login fields first. Clean them straight away so you are not passing raw input around.
Suggested commit: feat: capture login form values

STEP 9: Add separate empty checks for each field
Goal: Give simple feedback instead of one vague failure.
Files to change: backend/login_handler.php
Hint: Treat missing email and missing password as two different checks, even if both end up on the same form.
Suggested commit: feat: add empty checks for login fields

STEP 10: Add the PHP filter for email
Goal: Cover the "PHP filters" requirement in the simplest possible way.
Files to change: backend/login_handler.php
Hint: This just means using PHP's built-in email validation, not making your own complicated rule.
Suggested commit: feat: add email filter validation

STEP 11: Store errors in sessions
Goal: Send messages back to the login page after validation fails.
Files to change: backend/login_handler.php, templates/login_page.php
Hint: Sessions are the bridge between pages. Keep them small: error text and old email value are enough.
Suggested commit: feat: store login validation errors in session

STEP 12: Redirect back to the login page on failure
Goal: Finish the invalid-login path cleanly.
Files to change: backend/login_handler.php
Hint: If validation fails, set the session messages first, redirect back to templates/login_page.php, then stop further processing.
Suggested commit: feat: redirect invalid login back to form

--------------------------------------------------
PHASE 3: CHECK LOGIN AGAINST THE DATABASE
--------------------------------------------------

STEP 13: Look up the user by email
Goal: See whether the submitted email exists in the users table.
Files to change: backend/login_handler.php, backend/db_connect.php
Hint: Use a prepared statement for the lookup. This is the safe, standard approach and helps with SQL injection prevention.
Suggested commit: feat: add user lookup by email

STEP 14: Handle the "user not found" case
Goal: Complete the failure path if the email does not exist.
Files to change: backend/login_handler.php
Hint: Use one simple login error. Do not over-explain which part was wrong.
Suggested commit: feat: handle unknown login email

STEP 15: Verify the password properly
Goal: Complete the actual authentication check.
Files to change: backend/login_handler.php
Hint: If the database stores hashed passwords, compare against the hash using PHP's password tools rather than plain-text matching.
Suggested commit: feat: verify password against stored hash

STEP 16: Create the login session on success
Goal: Mark the user as signed in.
Files to change: backend/login_handler.php
Hint: Keep it minimal. A login flag, user id, and username are enough for this assignment level.
Suggested commit: feat: create session after successful login

STEP 17: Redirect valid login to the secure page
Goal: Finish the success path.
Files to change: backend/login_handler.php, templates/dashboard.php
Hint: Pick one secure page as the landing page after login. Your dashboard is the obvious choice in this project.
Suggested commit: feat: redirect successful login to dashboard

--------------------------------------------------

STEP 18: Protect the secure pages with a session check
Goal: Stop users opening protected pages by typing the URL directly.
Files to change: templates/dashboard.php, templates/profile.php, templates/create_post.php, templates/marketplace.php
Hint: Start with dashboard first. Once it works, repeat the same idea on the other secure pages.

STEP 19: Build a basic logout flow
Goal: Let the user end the session properly.
Files to change: backend/logout.php
Hint: Logging out should clear session data, destroy the active session, and remove any login-related cookie if you created one.

STEP 20: Add one small extra and then test everything
Goal: Finish the assignment requirements without overbuilding.
Files to check: whole project
Hint: The easiest extra feature is usually a simple cookie, such as remembering the last email used or showing a welcome-back message. Then test every route from start to finish.
Suggested commit: feat: add small extra feature and complete testing

--------------------------------------------------
WHAT "PHP FILTERS" MEANS
--------------------------------------------------

For this assignment, keep it very basic:
- Use PHP's built-in filter for checking whether an email looks valid.
- You do not need anything fancy.
- This is usually just one validation step in the login or registration process.

--------------------------------------------------
WHAT COUNTS AS XSS PREVENTION HERE
--------------------------------------------------

At this level, the safest simple rule is:
- Clean input when you receive it.
- Escape output when you display it.
- Any value shown back on the page, such as an error message, username, or old form value, should be treated carefully.

--------------------------------------------------
FEATURES OFTEN MISSING FROM EARLIER ASSIGNMENTS
--------------------------------------------------

If your teacher says "features missing from previous assignments", it usually means things like:
- Proper server-side validation, not just HTML required fields
- Escaping output to reduce XSS risk
- Using sessions for login state and messages
- Redirecting after success or failure
- Protecting secure pages from direct access
- Logging out properly
- Using prepared statements for database work
- Using hashed passwords instead of plain text

--------------------------------------------------
FINAL TEST CHECKLIST
--------------------------------------------------

Before you call it done, test these one by one:
- Submit the form with both fields empty
- Submit with email only
- Submit with password only
- Submit with an invalid email format
- Submit with an email that is not in the database
- Submit with a correct email but wrong password
- Submit with correct login details
- Try opening dashboard without logging in
- Log in and then open the secure pages
- Log out and try going back to the secure page again
